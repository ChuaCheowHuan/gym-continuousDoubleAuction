# File and triage issues the way this repository keeps them

Every finding is an issue (CLAUDE.md rule 8). The register in `docs/15` lists what is open, and
`docs/29` lists what is fixed, under the original IDs. This skill keeps the tracker and those
two documents saying the same thing.

## Filing a confirmed finding

Only file what `cda-verify-finding` confirmed. Search first, with
`gh api -X GET search/issues -f q='repo:ChuaCheowHuan/gym-continuousDoubleAuction <keywords>'`.
If the finding is already tracked, comment on that issue instead of filing a new one.

- **Title:** the defect in one sentence, in the user's terms (what happens, not the fix).
- **Body:** *What happens*, *Reproduced* (commit SHA, commands, raw output), *Impact* or
  *Scope*, *Suggested fix*. End with `_Generated by [Claude Code](https://claude.ai/code)_`.
- **Labels:** one severity (`S1-blocking`, `S2-major`, `S3-moderate`, `S4-minor`), one kind
  (`bug`, `enhancement`, `documentation`, `test-gap`, `refactor`, `question` when not
  reproduced), `security` when it applies, and exactly one of `agent` / `human` (below).
- **Type:** Bug, Task or Feature, through the GitHub MCP `issue_write` tool's `type`
  parameter. The REST create call does not set it.
- No `#fragment` links: the proxy wrapped some in backticks. Link to files.

## agent or human

- `agent`: an AI agent can finish it end to end in a session (code, tests, docs) with no
  decision outstanding.
- `human`: it needs a person. That means a choice between designs (also add `needs-decision`),
  a merge or a repository setting, compute an agent session cannot spend (an at-scale training
  run), or access an agent does not have.
- **Both:** split it. Create the parts as sub-issues (`issue_write` with
  `parent_issue_number`), one label each, and give the parent both labels. Typical split: the
  decision (`human`), then the code that follows from it (`agent`), or the run (`human`) and
  the write-up (`agent`).

## Triage pass

1. List the open issues (`gh api 'repos/<owner>/<repo>/issues?state=open&per_page=100'`;
   entries with `pull_request` are PRs, so skip them).
2. For each, read the body and comments and check the code on `master`:
   - **Done:** the fix merged, so close it as `completed` with a comment naming the PR or
     commit. Then move its finding from docs/15 to docs/29.
   - **Duplicate:** close it as `duplicate` (`duplicate_of`) with a comment pointing at the
     one kept. Keep the older or better-specified one.
   - **A request, not a defect** (for example "do a security review"): once its findings are
     filed, make them its sub-issues and close it as `completed`.
   - **Several independent fixes in one issue:** split them into sub-issues.
3. Label every open issue `agent` or `human`, per the rule above.
4. Report what you closed, merged and split, with numbers, in one list.

## Guardrails

- Closing needs a comment first. Always set `state_reason`.
- A sub-issue can have only one parent. Adding it to a second parent fails; check
  `issues/<n>/sub_issues` first.
- A label that does not exist makes `issue_write` fail (it is not auto-created). Create it
  first, or rename an equivalent one.
- Do not open a PR from a triage pass unless asked (CLAUDE.md rule 8).
