# Verify a finding before it costs anything

In the last full review about 64 raw findings reduced to 24 confirmed ones. The rest were false
positives, unreachable, or already tracked. Never rest a fix or an issue on an unverified claim.

## Steps

1. **Restate the claim as a falsifiable scenario with concrete numbers** (prices, sizes, cash,
   which agent acts when).
2. **Reproduce it on the current source** in a scratch script outside the repo (the session
   scratchpad). Keep the raw output.
3. **Run the inverse** (a case that should pass). A repro that cannot distinguish the two is not
   a repro. Example of a bad one: a second bid at the same price *replaces* the first, so it
   shows nothing; use different prices.
4. **Check the scenario is reachable.** Can the env, the config or RLlib produce that state?
   Each of these rules out a class of reviewer scenarios: one action per trader per step;
   self-match prevention runs first; the agents share one action-space object; the mark price
   is shared.
5. **Check the measure as well as the code.** A stress test that counts `cash + cash_on_hold < 0`
   also counts traders who are legitimately under water; scope it before trusting it.
6. **Classify:** confirmed, false positive, unreachable, real but already tracked, or cannot
   reproduce.
   - Search first: `doc/15_findings_and_recommendations.md` and the open issues
     (`search_issues` with the repo and a keyword).
   - Already tracked: add a comment to the existing issue, do not file a duplicate.
   - Cannot reproduce: file with the `question` label and say so.
7. **Confirmed:** if the task is to fix it, write the failing test first and prove it fails on the
   previous source (`git stash push -- gym_continuousDoubleAuction/envs`, run, `git stash pop`).
   If the task is a review ("do not fix new issues"), file it instead.

## Filing a confirmed finding

- Labels: a severity (`S1-blocking`, `S2-major`, `S3-moderate`, `S4-minor`) plus `bug`,
  `enhancement`, `documentation`, `test-gap`, `refactor` or `question`.
- Set the issue **type** (Bug, Task or Feature) through the GitHub issue tool's `type` parameter.
  The REST create call did not set it. Read it back in the UI.
- Do not use `#fragment` links in issue text; the proxy wrapped some in backticks. Link to files.
- End the body with `_Generated by [Claude Code](https://claude.ai/code)_`.

## Guardrails

- Report false positives to the user, with the reason; do not drop them silently.
- Do not edit `doc/16` or `doc/17` history to record a dropped finding. New facts get a new section.
